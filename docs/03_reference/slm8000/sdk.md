# SLM8000 のソフトウェアパッケージ

SLM8000 のソフトウェアパッケージ（通信ライブラリの本体、ヘッダーファイルなど）は、[sdk/](sdk/) フォルダに置きます。
設計の検討で、構造体や定数の正確な定義を確かめるために使います。

第 1 段階のアプリは RTMC64-EC だけを対象にしています（[ADR-001](../../02_design/decisions/ADR-001_phase1-scope.md)）。
SLM8000 は、設計のときに常に 2 番目に置く機種です。インターフェース・構造体・クラスなどを決めるときに、あとで両方の機種に対応できるかを判断する材料にします（2026-11-19 Shunsuke、[バックログ B-003](../../02_design/backlog.md)）。

> **`sdk/` フォルダの中身は Git に入れません。**
> ソフトウェアパッケージとライブラリ本体は、製品を購入した人だけが入手できるものです（[.gitignore](../../../.gitignore) の「製品のソフトウェアパッケージ」）。
> そのため、クローンした直後は `sdk/` フォルダがありません。
> マニュアル（[source/](source/)）は、ホームページでユーザー登録すれば読めるので、Git に入れています。

## クローンしたあとにやること

1. ソフトウェアパッケージを入手します。入手先は **未整備** です（分かる方は追記してください）。
2. `docs/03_reference/slm8000/sdk/` フォルダを作り、パッケージを手を加えずにその下へ置きます。フォルダ名は、パッケージの元の名前（例: `Slm8000_V280A`）のままにします。
   ```
   docs/03_reference/slm8000/
   ├─ sdk.md               ← この資料（Git で共有）
   └─ sdk/
       └─ Slm8000_V280A/   ← パッケージの中身（Git に入れない）
   ```
3. `git status` で、パッケージのファイルが表示されないことを確かめます。

## TPC ロギングについて分かったこと（2026-11-19）

マニュアル（TB00-1134 送受信データ、TB00-1131 セッティング PC、TB00-1132 ROMSW 設定ソフト）とパッケージ 2.8.0A を照らし合わせて分かったことです。
マニュアルはまだ Markdown にしていないので、PDF の文字を読んで照合しました。

| 項目 | 分かったこと | 根拠 |
|---|---|---|
| コマンドの並び | 設定（`REQ_TPCSEL_EX` 0x3E）→ 開始（`REQ_TPCLOG` 0x32。0 停止、1 開始、2 再開）→ 状態（`DAT_TPCINFO_EX` 0x2A）とデータの読み出し。RTMC64-EC と同じ | TB00-1134 4-2-59、4-2-60、4-1-27、`SyncdefCSNET.cs` |
| ロギング種別の値 | 0: ポジション・入出力（2ch）、1: 64ch、10: Ethernet ログ。10 はマニュアル（4-2-59）に載っていない | TB00-1134 4-2-59、`Slm8000dataCSNET.cs` の `TPCH_LOG_*` |
| 64ch のデータの読み出し | `DAT_TPCDATA_64`（0x2b）を使う。2ch は `DAT_TPCDATA`（0x25） | TB00-1134 4-1-24、4-1-25、`McWrapTpc.py` |
| ロギング項目の番号 | 指令位置 0、機械位置 1、偏差量 2、…、仮想指令位置 6、…、出力信号 15 の 16 項目。マニュアルと一致 | TB00-1134 4-2-59、`Slm8000dataCSNET.cs` の `TPCS_64_I_*` |
| 属性 | タスク番号 0～7、軸番号 0～8、マクロ変数番号 1000～9999、IO 信号番号 0～798 | TB00-1134 4-2-59 |
| 構造体 | 64ch の設定の構造体は 1 チャンネル 40 バイト、全体 2,568 バイト。C# の宣言はどれも `Pack = 4`。RTMC64-EC と同じ形 | TB00-1134 4-2-59、`Slm8000dataCSNET.cs` |
| データ 1 点の大きさ | 2ch は 16 バイト（`TPCDAT_POS`）、64ch は 4 バイト × チャンネル数 | TB00-1134 4-1-24、4-1-25 |
| バッファ | コントローラのロギングバッファは最大 65,536 バイト。読み出すと、その分のバッファが空く。読み出しが間に合わずにバッファが一杯になると、ロギングが止まる | TB00-1134 4-1-24、4-1-27 |
| ロギング周期の単位 | マニュアルでは **msec**（1～32767）。0 は制御周期ごと。制御周期の単位に丸める（例: 制御周期 2 msec、ロギング周期 5 msec なら 4 msec）。RTMC64-EC と同じ考え方で、マニュアルが正しい。Python のラッパーの説明「制御周期間隔」は誤り（2026-11-19 Shunsuke 確認） | TB00-1134 4-2-59、TB00-1131 4-2-8-2、`McWrapTpc.py` の `TpcDataPos.__init__` |
| 制御周期 | ROMSW の「サーボ制御周期(msec)」で設定する。既定値は 2.0。パルスジェネレータクロックとの組み合わせの表には、0.5、1、2、4、8 msec がある | TB00-1132 6-1-1、6-4 |
| 制御周期の設定値の読み方 | 設定値は、ドライバの設定ファイル `slm8000drv.ini` からしか読めない。ROMSW の設定で CPU に設定した割り込み周期を、ドライバがこのファイルに書き出している（2026-11-19 Shunsuke 確認）。Python のラッパーは、`[Program]` セクションの `RTCTime`（制御サンプリング周期、μsec、500～4000）として読んでいる。ファイルは通信ライブラリと同じフォルダに置く前提（サンプルのパス `./lib/slm8000drv.ini`）。パッケージには入っていない（現場の PC で作られる） | `pyslm8000/McIniParser.py`、`example/example_Direct_API.py` |
| `DAT_CYCLETIME` で読める値 | `DAT_CYCLETIME`（0x91）で構造体 `CYCLETIME` を読む。中身は `CycleTimeMax`（最大サイクリック周期）と `CycleTimeNow`（現在サイクリック周期）、単位 μs。`CycleTimeNow` は **問い合わせた瞬間の値** で、設定値ではない。この値をもとに平均を計算するなどに使う（2026-11-19 Shunsuke 確認）。なお、セッティング PC の「制御周期モニタ」（RtcMonitor）は、RTC を「割り込み処理の実行時間」と説明し、画面例では最大 192、平均 93、現在 93 μsec を表示している（TB00-1131 4-2-8-8）。`CycleTimeNow` は、処理時間ではなく **実際の周期** である（2026-11-19 Shunsuke 確認）。RTMC64-EC の `CYCLETIME`（`CycleTime` の 1 つ）と中身が違う。マニュアル（TB00-1134）には載っていない | `SyncdefCSNET.cs`、`Slm8000dataCSNET.cs` の `CYCLETIME` |
| 読み出しの流れ（手本） | RTMC64-EC の Python ラッパーと同じ。別スレッドで、状態（`DAT_TPCINFO_EX`）を読んでバッファにある分を全部読み出す、を一定の間隔（既定 0.05 秒）でくり返す。止める指示をしていないのにロギングが止まっていたら、バッファが一杯になったと判断する | `McMain.py` の `start_tpc`、`__fetch_tpc_data` |
| セッティング PC | TPC ロギング画面は「ポジション」と「64CH」の 2 つのタブがあり、今のセッティング PC は 64ch でも記録できる（2026-11-19 Shunsuke 確認）。本文の「任意の2軸分の座標をロギング」は古い記述。「常時」アップロードは、ロギングが 2 msec 以下だと間に合わずに止まる、とも書いている | TB00-1131 4-2-8-2 |

## 通信設定ファイル（slm8000drv.ini）

- `slm8000drv.ini` に、コントローラとの通信設定（通信の種類、IP アドレスなど）と、制御周期の設定値（`[Program]` の `RTCTime`）が書かれている。セッティング PC と ROMSW 設定ソフトは、この通信設定を参照している。このアプリも同じファイルを参照すれば、同じコントローラにつなげる。RTMC64-EC の `rt64ecdrv.ini` と同じ設計（2026-11-19 Shunsuke）。
- ini の中身は内部設計なので、マニュアルには載っていないことがある。キーの名前は Python のラッパー（`pyslm8000/McIniParser.py`）で分かる。セクションは `[Communication]`、`[Program]`、`[Task0]`～`[Task7]`、`[I/O Port]`、`[Option]` で、RTMC64-EC と同じ。

## RTMC64-EC との違い（設計で気をつけること）

取得部品を機種ごとに分ける（constitution 原則 III）ときに、機種ごとに持たせる必要があるものです。

| 項目 | RTMC64-EC | SLM8000 |
|---|---|---|
| 64ch のロギング種別の値 | 2 | 1 |
| 仮想指令位置の項目番号 | 19 | 6 |
| 64ch のデータを読むデータタイプ | `DAT_TPCDATA` | `DAT_TPCDATA_64`（0x2b） |
| 制御周期の設定値の読み方 | `DAT_CYCLETIME` で `CYCLETIME.CycleTime`（制御周期、μs）を読む | `DAT_CYCLETIME` では実際の周期（`CycleTimeMax`、`CycleTimeNow`）しか読めない。設定値は `slm8000drv.ini` の `[Program]` `RTCTime`（μs）から読む |
| つなぎ方 | 同じ PC の中で、共有メモリを使う | 別の基板（AS710）に、イーサネットか RS-232C でつなぐ。接続の設定（構造体 `SXDEF`）で通信の種類、IP アドレス、COM ポートを指定する |
| バイトの並び | PC と同じ（リトルエンディアン） | コントローラはビッグエンディアン。通信ライブラリにバイトの並びを変える関数（`DatEndianChange`）がある。TPC データの読み出しで変換が要るかは未確認（Python のラッパーは TPC データにこの関数を使っていない） |
| 接続先の設定 | `rt64ecdrv.ini` の `[Communication]` | `slm8000drv.ini` の `[Communication]`（同じ設計） |
| 物理軸の数 | 64 | 8 |
| タスクと論理軸 | タスク 8、論理軸 9 | 同じ |
| 通信ライブラリの DLL | `Rt64eccomnt.dll` / `Rt64eccomnt64.dll` | `slm8000comnt.dll` / `slm8000comnt64.dll` |

通信で読み出すので、読み出しの遅れは RTMC64-EC より大きくなる見込みです。とくに RS-232C では、ロギング周期とチャンネル数によっては、読み出しが間に合わないおそれがあります（6ch・2 msec なら 1 秒あたり 12,000 バイト）。実際の速さは確かめていません。

## 注意

- パッケージの中身は書き換えません。Claude Code は、権限設定で `sdk/` の下の書き換えを拒否されています（[.claude/README.md](../../../.claude/README.md)）。
- パッケージに入っているプログラム（サンプル、ドライバ、設定ソフト、ファームウェア書き込みなど）は、ビルドも実行もしません。軸を動かしたり、コントローラの状態を変えたりするおそれがあるためです（[constitution](../../../.specify/memory/constitution.md) 原則 I）。
- ヘッダーなどの中身を、Git に入るファイルにそのまま写さないでください。設計に必要な点は、この資料のように、要点と、どのファイルにあるかを書くにとどめます。
