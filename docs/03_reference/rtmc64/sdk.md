# RTMC64 のソフトウェアパッケージ

RTMC64 のソフトウェアパッケージ（通信ライブラリの本体、ヘッダーファイルなど）は、[sdk/](sdk/) フォルダに置きます。
設計の検討で、構造体や定数の正確な定義を確かめるために使います。

> **`sdk/` フォルダの中身は Git に入れません。**
> ソフトウェアパッケージとライブラリ本体は、製品を購入した人だけが入手できるものです（[.gitignore](../../../.gitignore) の「製品のソフトウェアパッケージ」）。
> そのため、クローンした直後は `sdk/` フォルダがありません。
> マニュアル（[source/](source/)）は、ホームページでユーザー登録すれば読めるので、Git に入れています。

## クローンしたあとにやること

1. ソフトウェアパッケージを入手します。入手先は **未整備** です（分かる方は追記してください）。
2. `docs/03_reference/rtmc64/sdk/` フォルダを作り、パッケージを手を加えずにその下へ置きます。フォルダ名は、パッケージの元の名前（例: `RT64EC_V310A`）のままにします。
   ```
   docs/03_reference/rtmc64/
   ├─ sdk.md               ← この資料（Git で共有）
   └─ sdk/
       └─ RT64EC_V310A/    ← パッケージの中身（Git に入れない）
   ```
3. `git status` で、パッケージのファイルが表示されないことを確かめます。

## 置いているパッケージ

開発機と同じ版を使います。版を変えたら、この表を直してください。

| フォルダ | 機種 | 版 | 置いた日 | 備考 |
|---|---|---|---|---|
| `sdk/RT64EC_V310A/` | RTMC64-EC | 3.1.0A（通信ライブラリは V190。`Version.sys` による） | 2026-11-19 | 第 1 段階で使う（[ADR-001](../../02_design/decisions/ADR-001_phase1-scope.md)）。2026-11-19 時点の最新版 |

開発機に入っている通信ライブラリの版と同じかは、まだ確かめていません。

## 中身の地図（RT64EC_V310A）

| 場所 | 中身 | 使い方 |
|---|---|---|
| `devlp/Lib-Com/` | 通信ライブラリ（32 ビット版 `Rt64eccomnt.dll` と 64 ビット版 `Rt64eccomnt64.dll`）、C/C#/VB/Python 用の宣言 | ★ アプリの設計で一番使う。C# 用は `Rt64eccomapiCSNET.cs`（32 ビット）、`Rt64eccom64apiCSNET.cs`（64 ビット）、`Rt64ecdataCSNET.cs`（構造体と定数）、`SyncdefCSNET.cs`（データタイプなどの番号）。文字コードは Shift_JIS |
| `devlp/pyrt64ec/` | Python 用のラッパーと説明（`man/` に HTML） | TPC ロギングの使い方の手本として読む（`pyrt64ec/McWrapTpc.py`、`McMain.py` の `start_tpc` など） |
| `devlp/CSNetSmpl/`、`CSNetSmpl64/` | C# のサンプルプログラム | 読むだけ。ビルド・実行しない |
| `devlp/EasySmpl/` ほか | C++ などのサンプル | 読むだけ |
| `devlp/Lib-Tcd/`、`Lib-Gcd/` | 運転プログラムの変換ライブラリ | 第 1 段階では使わない |
| 直下の `*.exe`、`flash/`、`rt64ecdrv.ini` | コントローラのドライバ、設定ソフト、ファームウェアなど | **実行しない**。コントローラの状態を変えるおそれがある |
| 直下の `L_*.txt`、`G_*.txt` | 運転プログラムのサンプル（直線、円弧など） | 読むだけ。テストで円や直線を動かすときの参考になるが、動かすのは人が安全を確かめてから |
| `Version.sys` | 版の一覧 | 版を確かめるときに読む |

## TPC ロギングについて分かったこと（2026-11-19）

マニュアル（[TB00-1044](converted/TB00-1044.md)）とパッケージ 3.1.0A を照らし合わせて分かったことです。設計（spec 002）の根拠にします。

| 項目 | 分かったこと | 根拠（パッケージ内のファイル） |
|---|---|---|
| ロギング種別の値 | 0: ポジション・入出力（2ch）、1: EtherCAT の PDO、2: 64ch。マニュアルの表の「0 固定」は誤りで、64ch は 2 を指定する。1（PDO）はマニュアルの 4-2-57 に載っていない | `Rt64ecdataCSNET.cs` の `TPCH_LOG_*` |
| ロギング項目の番号 | 指令位置 0、機械位置 1、仮想指令位置 19。マニュアルと一致 | 同 `TPCS_64_I_*` |
| 64ch モードのデータ 1 点の大きさ | 4 バイト × 設定したチャンネルの数。6ch なら 24 バイトで、バッファ（65,536 バイト）に約 2,730 点入る | `McWrapTpc.py` の `TpcData64CH.element_size` |
| 構造体の並び | C# の宣言はどれも `Pack = 4`。64ch の設定の構造体は 1 チャンネル 40 バイトで、マニュアルと一致 | `Rt64ecdataCSNET.cs` |
| ロギング周期の単位 | マニュアルと C# の宣言は「ms」、Python のラッパーは「制御周期の間隔。0 のときは毎制御周期」と説明している。**食い違っている**ので、実機で確かめる | TB00-1044 4-2-57、`McWrapTpc.py` の `TpcDataPos.__init__` |
| 読み出しの流れ（手本） | 設定（REQ_TPCSEL_EX）→ 開始（REQ_TPCLOG = 1）→ 別スレッドで、状態（DAT_TPCINFO_EX）を読んでバッファにある分を全部読み出す、を一定の間隔（既定 0.05 秒）でくり返す。読み出した大きさが 1 点の大きさで割り切れなければ異常とする。止める指示をしていないのにロギングが止まっていたら、バッファが一杯になったと判断する | `McMain.py` の `start_tpc`、`__fetch_tpc_data` |
| 32 ビットと 64 ビット | 通信ライブラリは両方ある。アプリをどちらで作るかは `/speckit-plan` で決める | `devlp/Lib-Com/` |

## 注意

- パッケージの中身は書き換えません。Claude Code は、権限設定で `sdk/` の下の書き換えを拒否されています（[.claude/README.md](../../../.claude/README.md)）。
- パッケージに入っているプログラム（サンプル、ドライバ、設定ソフトなど）は、ビルドも実行もしません。軸を動かしたり、コントローラの状態を変えたりするおそれがあるためです（[constitution](../../../.specify/memory/constitution.md) 原則 I）。
- ヘッダーなどの中身を、Git に入るファイルにそのまま写さないでください。設計に必要な点は、この資料のように、要点と、どのファイルにあるかを書くにとどめます。
