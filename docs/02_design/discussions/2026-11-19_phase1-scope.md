## 案

### 案 A: TPC-Excel の置き換えだけ（#1, #2, #12）

- 内容: CSV を読み込み、TPC-Excel と同じ 3 つの解析とグラフを出す。印刷・画像保存もできる。
- 良い点: 範囲が小さく、早く出せる。実機につながないので安全面の作り込みが少ない。原則 II の一致確認に集中できる。
- 気になる点: 目的 2（取得から解析まで 1 つのアプリで）を満たさない。ユーザーから見て TPC-Excel との違いが「Excel が要らない」だけで、進化版と言いにくい。

### 案 B: A ＋ コントローラからの取得（#1〜#3, #5, #12）

- 内容: 案 A に加え、2ch モードでコントローラから直接ロギングし、読み出して解析できる。取得したデータは CSV に保存できる。
- 良い点: 企画書の目的 1、2 を満たす。取得・保持・表示・解析の部品の分け方（原則 III）を最初から実物で確かめられる。後の 64ch モードや他製品への土台になる。
- 気になる点: 原則 IV（バッファの監視、欠けの記録）と、実機での確認の手順が必要になる。

### 案 C: B ＋ 解析の進化点（#1〜#3, #5〜#9, #12）

- 内容: 案 B に加え、数値の指標、自動推定、符号つき表示、追従誤差を入れる。
- 良い点: 「良し悪しを数値で判断できる」という、ユーザーにとって分かりやすい進化が入る。デモで違いを見せやすい。
- 気になる点: 指標の定義を決める作業が増える。TPC-Excel に答えがないので、正しさの確かめ方（手計算、別の道具との比較など）を決める必要がある。

### 案 D: C ＋ リアルタイム表示・長時間記録（#1〜#3, #5〜#12）

- 内容: 5-4 の進化点をほぼすべて入れる。
- 良い点: 企画書の進化点を一度に満たす。
- 気になる点: 範囲が大きく、最初のリリースが遅れる。リアルタイム表示と長時間記録は、読み出しの遅れ（原則 IV）と表示の性能の両方に関わり、検証が重い。

> 2026-11-19 追記: この提案のあと、案 C を基本にし、#5 と #11 も入れることが決まった（「ここまでに決まったこと」）。spec の分け方は「spec の分け方（案）」に書き直した。下は最初の提案として残す。

案 B を第 1 段階の土台にし、案 C の項目は spec を分けて順に入れるのがよいと考える。

- 最初の spec（001）: CSV 読み込みと 3 つの解析（TPC-Excel と同じ計算）とグラフ表示。原則 II の一致確認をここで固める。
- 次の spec（002）: コントローラからの取得（2ch モード）と CSV 保存。原則 I・IV の対応をここで固める。

## spec の分け方（案）

段階ごとに動作を確かめられるよう、確かめ方が違うところで分ける。

| spec | 中身 | 動作の確かめ方 | 実機 |
|---|---|---|---|
| 001 | 画面の土台（解析を追加できる作り）、TPC-Excel 形式の CSV 読み込み、3 つの解析（TPC-Excel と同じ計算）、グラフ表示、グラフの印刷・画像保存 | TPC-Excel のサンプルデータ（サーボ応答用 3 つ、真円用 2 つ）で、TPC-Excel と結果が一致することを自動テストで確かめる（原則 II） | 不要 |
| 002 | コントローラからの取得（64ch モードで 2 軸 × 3 種類の位置、読み続けて長く記録、バッファの監視、欠けの検出と通知）、CSV 保存、長いデータの表示 | 自動テストは DLL をモックに差し替えて行う（欠けやバッファが一杯の場合も再現する）。最後に開発機の実機で、取得 → 保存 → 001 の解析までを確かめる | 必要（人が安全を確かめてから） |
| 003 | 解析の進化点（3 つの位置の比較、数値の指標、中心・基準直線の自動推定、符号つきのずれ、追従誤差） | 作ったデータ（答えが分かっている円や直線、ステップ応答など）で計算を確かめる。自動推定は、TPC-Excel のサンプルデータで手入力の場合と比べる | 不要 |

- 001 を先にすると、実機の心配なく、画面の土台と TPC-Excel との一致を固められる。
- 002 と 003 は互いに依存しないので、順番を入れ替えてもよい。
- 003 は大きければ、解析ごと（サーボ応答、真円、直線）に分けてもよい。

## メモ

- 関係する別の論点: 「TPC-Excel の今後の扱い（並行して提供するか、置き換えるか）」。置き換えるなら、案 A の範囲（印刷を含む）は第 1 段階で必須になる。

### コントローラからの取得で決めること（2026-11-19）

[送受信データ マニュアル TB00-1044](../../03_reference/rtmc64/converted/TB00-1044.md) の 4-1-15、4-1-16、4-2-43、4-2-53 を読んで分かったことと、そこから出てくる問い。

- 分かったこと
  - 2ch モードの 1 点は 16 バイト（2 軸の位置と、それぞれの汎用入力 1 点・汎用出力 1 点の状態）。バッファは最大 65,536 バイトなので、約 4,096 点。
  - DAT_TPCDATA はロギング中でも読み出せ、読み出した分のバッファが空く。読み続ければバッファより長く記録できる。間に合わないとロギングが止まる。
  - REQ_TPCSEL（データの選択）は、ロギングしていないときだけ送れる。REQ_TPCLOG は開始・停止・再開を送る。
  - REQ_TPCSEL では、軸ごとに指令位置か機械位置かを選べる。サーボ応答精度（1 軸の指令位置と機械位置）も、真円・直線（2 軸の機械位置）も 2ch モードで足りる。
- 問い
  - [ ] **読み続けて記録するか**。バッファの分だけなら、4 ms 周期で約 16 秒。低速の円などでは足りないおそれがある。読み続けるなら、32,000 点を超える記録（#11）も実質的に扱うことになる。
  - [x] **ロギング周期の指定をどのコマンドで行うか** → REQ_TPCSEL_EX（4-2-57）のヘッダに「ロギング周期」（ms、0〜32767）がある。2ch モードでも 64ch モードでも、REQ_TPCSEL_EX で指定する。
  - [ ] **軸の動かし方**。アプリは運転の指令を送らない（原則 I）ので、円や直線の動作は、セッティング PC やユーザーのプログラムで別に動かす。利用者の手順として spec に書く必要がある。
  - [ ] **セッティング PC との同時使用**。セッティング PC も TPC ロギングを操作できるので、両方から操作したときにどうなるか（ロギングの取り合い）を確かめ、扱いを決める。
  - [ ] **ロギングの開始と停止のきっかけ**。利用者のボタン操作だけにするか、点数や時間で自動で止めるか。
  - [ ] **開発機と実機での確認**。開発機は RTMC64-EC か。実機での確認は人が安全を確かめてから行う（原則 I）。

### 取得するデータ: 2 軸 × 3 種類の位置（2026-11-19、Shunsuke 提案）

**提案の内容**

- TPC-Excel は、2 軸の機械位置（エンコーダのフィードバック）だけを取り、利用者が入力した理想の軌跡と比べていた。
- RTMC64-EC では、次の 3 種類の位置を軸ごとに同時に取れる。2 軸で 6ch になる。
  - **仮想指令位置**: 理想の軌跡そのもの。
  - **指令位置**: 仮想指令位置にフィルターをかけたもの。実際にサーボに払い出す指令。
  - **機械位置**: エンコーダのフィードバック。
- 3 つを比べると、軌跡のずれがどこで生じたかを分けて調べられる。
  - 仮想指令位置と指令位置の比較: 指令（フィルター）による軌跡への影響。
  - サーボアンプ側の制御による軌跡への影響（比べる組み合わせは下の問いを参照）。
- 理想の軌跡を直接記録するので、円の中心・半径や基準直線を確実に求められる。

**マニュアルで確かめたこと**（[TB00-1044](../../03_reference/rtmc64/converted/TB00-1044.md) 4-2-57、4-1-23）

- 6ch を取るには 64ch モード（REQ_TPCSEL_EX、ロギング種別 2）が要る。2ch モード（REQ_TPCSEL）で選べる位置は、指令位置と機械位置だけで、2 つまで。
- RTMC64-EC の 64ch モードのロギング項目に、指令位置（0）、機械位置（1）、仮想指令位置（19）がある。どれも 4 バイト（long）。属性で、タスク番号と軸番号を指定する。
- ロギング周期は REQ_TPCSEL_EX のヘッダで指定する（ms）。
- DAT_TPCINFO_EX で、バッファの使用量と空き容量（バイト）を読める。読み続けるときの監視に使える。
- マニュアルの用語の説明には「仮想指令位置」の定義が見当たらない。上の意味はユーザーズマニュアル（TB00-1040、未変換）などで確かめる。

**Claude の評価**

- 採用してよいと考える。ユースケース（3 つの解析）は変えずに、解析の質を上げる提案で、「制御と完全に同期した記録」という TPC ロギングの強みがよく活きる（企画書 6 章の「TPC ロギングらしさ」）。
- 影響
  - 取得（spec 002）は 64ch モードで作る。2ch モードは要らなくなるかもしれない。
  - 解析（spec 003）に「3 つの位置の比較」が加わる。中心・基準直線の推定は、仮想指令位置から求められる。
  - TPC-Excel 形式の CSV（2 列）は、引き続き読めるようにする（原則 II）。その場合、仮想指令位置がないので、中心・基準直線は手入力か、機械位置からの推定になる。
  - CSV 保存の形式は 6 列が基本になる。TPC-Excel 形式（2 列）でも書き出せるようにするかを決める。

**問い**

- [x] **サーボアンプ側の影響を見る組み合わせ** → 3 つの組み合わせをすべて見せる。選ぶ形にする場合は「仮想指令位置と機械位置」を最初に選ばれた状態にする（2026-11-19）
- [ ] **TPC-Excel 形式（2 列）で書き出すときの列**。真円・直線なら「X 軸の機械位置、Y 軸の機械位置」、サーボ応答なら「1 つの軸の指令位置、機械位置」が TPC-Excel の使い方に合う。利用者が選ぶか、解析の種類で決めるか。
- [ ] **サーボ応答精度で取るデータ**。サーボ応答精度は 1 軸の解析。1 軸 × 3 種類（3ch）を取るか、いつも 2 軸 × 3 種類（6ch）を取って軸を選ぶか。
- [x] **データ 1 点の大きさ** → 選んだチャンネルの数で変わる（4 バイト × チャンネル数。6ch なら 24 バイトで約 2,730 点）。ソフトウェアパッケージ 3.1.0A の Python ラッパーで確かめた（[sdk.md](../../03_reference/rtmc64/sdk.md)）。実機でも確かめる。
- [ ] **3 つの位置の時間のずれ**。機械位置は、指令を出してからフィードバックが返るまでの通信の遅れを含むはず。比べるときに、この遅れをどう扱うか（そのまま見せるか、補正するか）。
- [x] **マニュアルの記載の食い違い** → 64ch は「2」が正しい。ソフトウェアパッケージ 3.1.0A の C# の宣言（`TPCH_LOG_64CH = 2`）で確かめた。
- [ ] **ロギング周期の単位**（新しく分かった食い違い）。マニュアルと C# の宣言は「ms」、Python ラッパーの説明は「制御周期の間隔」。実機で確かめる。

### 画面の構成: MDI で、解析ごとに子ウインドウを作る案（2026-11-19、Shunsuke 提案）

ユースケースは将来増える想定なので、追加しやすい作りとして提案された。

- 良い点
  - 解析ごとに画面が分かれ、新しい解析を足しても既存の画面に触れずに済む。
  - 複数の画面を並べて比べられる（調整前と後の真円精度など）。
  - WinForms（.NET Framework）の標準機能で作れ、追加のライブラリが要らない。
- 気を付けること
  - 親ウインドウのメニューに解析の名前を書き込まない。各解析が共通のインターフェイスで「名前」と「子ウインドウの作り方」を返し、親はその一覧からメニューを組み立てる。書き込むと、解析を足すたびに親を直すことになり、原則 III に反する。
  - 子ウインドウは「ユースケースごとに 1 つ」ではなく「開いた解析ごとに 1 つ」にする。同じ解析を別のデータで開いて比べられるようにするため。
  - データは子ウインドウに持たせず、保持の部品に置く。1 つのデータを複数の解析で見られるようにするため（原則 III）。
  - 標準の MDI は見た目が古く、高 DPI で崩れることがある。代わりにタブやドッキングの方式（DockPanel Suite など）もあるが、外部ライブラリが増える。
- 扱い
  - MDI を使うかどうかは実装の方式なので、spec.md には書かず、`/speckit-plan` で決める。そのとき、この検討を入力として渡す。
  - spec.md には、利用者から見た要求として「複数の解析結果を同時に開いて並べられる」「解析は既存の機能を変えずに追加できる」を書く。
