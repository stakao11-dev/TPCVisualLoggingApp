# ADR-001: 第 1 段階に入れる機能の範囲

- **ステータス**: 決定（決定 / 置き換え済み）
- **決定日**: 2026-11-19
- **関係者**: Shunsuke
- **検討メモ**: [2026-11-19_phase1-scope.md](../discussions/2026-11-19_phase1-scope.md)
- **反映先の仕様**: 未反映（spec 001〜003 に反映する予定）
- **置き換えた ADR / 置き換えられた ADR**: なし

## 背景

企画書 7 章では、第 1 段階（最初のリリース）を「TPC-Excel の 3 つの解析を使えるようにする」としていた。しかし、TPC-Excel をどこまで超えるか（企画書 5 章の「アプリで加える機能（案）」と 5-4 の進化点のどれを入れるか）は決まっておらず、最初の spec を書けなかった（企画書 10 章）。

## 決定

### 対象

- ユースケースは、TPC-Excel から引き継ぐ 3 つ（サーボ応答精度、真円精度、直線精度）に限る。企画書 5-5 の新しいユースケースの候補は入れない。
- 対応する機種は RTMC64-EC だけにする。開発機も RTMC64-EC。

### 取得

- コントローラから直接ロギングし、データを読み出せるようにする。
- 軸ごとに次の 3 種類の位置を同時に取る。2 軸で 6ch。64ch モード（REQ_TPCSEL_EX）を使う。
  - 仮想指令位置: 理想の軌跡（RTMC64-EC のロギング項目 19）
  - 指令位置: 仮想指令位置にフィルターをかけ、サーボに払い出す指令（同 0）
  - 機械位置: エンコーダのフィードバック（同 1）
- 読み続けることで、コントローラのバッファより長く記録できるようにする。32,000 点（TPC-Excel の上限）を超えるデータも扱う。
- 取得したデータは CSV に保存できる。6 列で保存でき、TPC-Excel 形式（1 行 1 点、2 列）でも書き出せる。
- ロギング中のリアルタイム表示は入れない。描画の負荷がログの読み出しを遅らせ、ロギングが止まるおそれがあるため（constitution 原則 IV）。将来の候補として [backlog.md](../backlog.md) の B-001 で管理する。

### 解析と表示

- TPC-Excel 形式の CSV を読み込み、3 つの解析を TPC-Excel と同じ計算で行える（constitution 原則 II）。
- 解析の進化点を入れる。
  - 3 つの位置の比較。次の 3 つの組み合わせをすべて見られる。選ぶ形にする場合は「仮想指令位置と機械位置」を最初に選ばれた状態にする。
    - 仮想指令位置と指令位置: 指令（フィルター）による軌跡への影響
    - 指令位置と機械位置: サーボ側の制御による軌跡への影響
    - 仮想指令位置と機械位置: 全体の影響（TPC-Excel と同じ見方）
  - 数値の指標（オーバーシュート量、整定時間、真円度、ずれの最大値など）
  - 円の中心・半径と基準直線の自動推定（仮想指令位置があればそこから求める）。手入力の方法も残す（原則 II）
  - 直線のずれの符号つき表示
  - 追従誤差の表示
- グラフを印刷・画像保存できる。

### spec の分け方

段階ごとに動作を確かめられるよう、3 つの spec に分ける。

| spec | 中身 | 動作の確かめ方 | 実機 |
|---|---|---|---|
| 001 | 画面の土台（解析を追加できる作り）、TPC-Excel 形式の CSV 読み込み、3 つの解析（TPC-Excel と同じ計算）、グラフ表示、印刷・画像保存 | TPC-Excel のサンプルデータで、結果が TPC-Excel と一致することを自動テストで確かめる | 不要 |
| 002 | コントローラからの取得（64ch モードで 2 軸 × 3 種類の位置、読み続けて長く記録、バッファの監視、欠けの検出と通知）、CSV 保存（6 列、2 列）、長いデータの表示 | 通信ライブラリをモックに差し替えて自動テストする。最後に開発機の実機で、取得から解析までを確かめる | 必要 |
| 003 | 解析の進化点（3 つの位置の比較、数値の指標、自動推定、符号つきのずれ、追従誤差） | 答えが分かっているデータで計算を確かめる。自動推定は、手入力の場合と比べる | 不要 |

001 を最初に作る。002 と 003 は互いに依存しないので、どちらを先にしてもよい。

## 却下した案と理由

| 案 | 却下した理由 |
|---|---|
| CSV の読み込みと TPC-Excel と同じ 3 つの解析だけ（案 A） | 取得から解析までを 1 つのアプリでできるようにする、という目的（企画書 3 章の 2）を満たさない。TPC-Excel との違いが「Excel が要らない」だけになる |
| 案 A にコントローラからの取得を足すだけ（案 B） | 結果が主にグラフで、良し悪しの判断が見る人の経験に頼る、という TPC-Excel の課題が残る |
| 2ch モードで 2 軸の機械位置だけを取る（TPC-Excel と同じデータ） | 理想の軌跡（仮想指令位置）と指令位置も同時に取れば、ずれが指令とサーボ側のどちらで生じたかを分けて調べられ、中心や基準直線も確実に求められる |
| リアルタイム表示も入れる（案 D） | 描画の負荷がログの読み出しを遅らせ、ロギングが止まるおそれがある（原則 IV）。将来の候補として残す |
| RTMC64-M3 にも対応する | 開発機が RTMC64-EC で、M3 は実機で確かめられない。将来の候補として残す（backlog B-002） |
| 1 つの spec にまとめる | 実機が要る部分と要らない部分を分け、段階ごとに動作を確かめるため |

## 影響

- 企画書 7 章の第 1 段階の対象製品（RTMC64 の -M3 / -EC）が、この決定（-EC だけ）と食い違っていた。企画書の 5-4、7 章、10 章をこの決定に合わせて直した（2026-11-19）。
- 取得（spec 002）では、constitution 原則 I（ロギングのコマンドだけを送る）と原則 IV（バッファの監視、止まったときの通知、欠けの記録）を満たす必要がある。実機での確認は、人が装置の状態と周りの安全を確かめてから行う。
- アプリは運転の指令を送らないので、円や直線の動作は、セッティング PC やユーザーのプログラムで別に動かす。この手順を spec に書く。
- 次のことは、spec にしてから `/speckit-clarify` で決める。検討メモの問いの欄に詳しく書いてある。
  - 64ch モードのデータ 1 点の大きさ（実機で確かめる）と、読み出しの間隔
  - 3 つの位置の時間のずれ（通信の遅れ）の扱い
  - TPC-Excel 形式（2 列）で書き出すときの列の選び方
  - サーボ応答精度で取るデータ（1 軸 × 3 種類か、2 軸 × 3 種類から選ぶか）
  - セッティング PC と同時に使ったときの扱い、ロギングの開始・停止のきっかけ
  - 数値の指標の定義と、正しさの確かめ方
  - 印刷・画像保存の細かい範囲
- 画面の構成（MDI で解析ごとに子ウインドウを作る案）は、`/speckit-plan` で決める。検討メモの記録を入力として渡す。
