## 1. 概要

テクノ製のモーションコントローラには、制御中のデータをリアルタイムで記録する **TPC ロギング** という機能があります。
TPCVisualLoggingApp は、この TPC ロギングのデータを取得・表示・解析する Windows アプリケーションです。

これまで TPC ロギングのデータは、Microsoft Excel 上で動く「**TPC-Excel**」（モーションアナライザ）で解析してきました。
TPCVisualLoggingApp は、**TPC-Excel を拡張した進化版** です。Excel に頼らない、テクノ独自のアプリケーションとして作ります。

まず TPC-Excel の 3 つの解析を引き継ぎます。そのうえで、社内のアイデア出しやユーザーへのヒアリングから新しいユースケースを見つけ、機能を増やしていきます。
そのアプリを通して、TPC ロギングを使うとどんな良いことがあるのかを、ユーザーに知ってもらうことが目的です。

## 2. 背景

### TPC ロギングとは

TPC（ツールパスチェッカー）ロギングは、コントローラの中のデータを、制御クロックに完全に同期して記録する機能です。
RTMC64 の場合、仕組みは次のとおりです（[送受信データ マニュアル TB00-1044](../03_reference/rtmc64/converted/TB00-1044.md) 4-1-15、4-2-43、4-2-57 ほか）。

| 項目 | 内容 |
|---|---|
| 記録できるデータ（2ch モード） | 2 軸分の位置（指令位置か機械位置）と、それぞれに汎用入力 1 点・汎用出力 1 点の状態 |
| 記録できるデータ（64ch モード） | 最大 64 チャンネル。チャンネルごとに、次の中から選べます。指令位置、機械位置、偏差量、トルク、全体・軸・タスクのステータスとアラーム、入力信号、出力信号、マクロ変数、時計、サーボ通信のデータ（M3 は MECHATROLINK のモニタ、EC は PDO） |
| 記録の間隔 | ロギング周期を指定できます（ms 単位） |
| 記録先 | コントローラの中のリングバッファ（最大 65,536 バイト。2ch モードで約 4,096 点） |
| 取り出し方 | PC アプリが通信ライブラリで読み出します。読み出した分はバッファが空くので、読み続ければバッファより長く記録できます |
| 注意点 | 読み出しが間に合わずバッファが一杯になると、ロギングが止まります |

使うコマンドは次のとおりです。

| コマンド | 役割 |
|---|---|
| REQ_TPCSEL / REQ_TPCSEL_EX | 記録するデータとロギング周期を選びます |
| REQ_TPCLOG | ロギングを開始・停止・再開します |
| DAT_TPCINFO / DAT_TPCINFO_EX | ロギング中かどうか、バッファの使用量を読みます |
| DAT_TPCDATA | 記録したデータを読み出します |

### 今の解析手段: TPC-Excel

TPC-Excel の説明書（[TB04-1478 Ver1.1](../03_reference/tpcexcel/source/TB04-1478-V11.pdf)、2011 年）と、Excel ファイルの中のマクロ（[取り出した VBA ソース](../03_reference/tpcexcel/converted/README.md)）を調べた結果をまとめます。

**使う手順**

1. セッティング PC（テクノ標準の運転ソフト）で、記録する 2 つの位置データとロギング周期を選び、ロギングします。
2. 記録したデータを CSV ファイルに保存します（1 行 1 点、2 列）。
3. TPC-Excel を開き、マクロを有効にします。
4. 解析方法を選び、CSV を読み込み、設定値を入力して解析します。

**解析機能**

| 解析 | 何を計算・表示するか |
|---|---|
| 合成軌跡 | 1 列目を横軸、2 列目を縦軸にして軌跡を描きます（簡易表示） |
| サーボ応答精度解析 | 位置の差分から速度（pulse/s）を求め、時間を横軸にしたグラフを描きます |
| 真円精度解析 | 理想円からの半径方向のずれを拡大して、円のグラフに描きます |
| 直線精度解析 | 理想直線からの垂直方向のずれと、その X 成分・Y 成分を、データ番号を横軸にしたグラフに描きます |

**分かった制約**

| 制約 | 内容 |
|---|---|
| Excel の版への依存 | Excel 2000/2003 向けの版（.xlt）と、Excel 2010 向けの版（.xltm）の 2 つがあります。解析の中身は同じですが、グラフ表示や印刷のマクロを Excel の版に合わせて直しています |
| 動作環境が古い | 説明書の対応 OS は Windows XP/Vista/7、対応 Excel は 2000/2003 です |
| 位置の 2 列だけを扱う | CSV の位置 2 列だけを使います。入出力の状態、ステータス、トルクなど、TPC ロギングで取れるほかのデータは扱えません |
| 点数の上限 | 取り込めるのは最大 32,000 点です（マクロの中で決め打ちされています） |
| 結果は主にグラフ | 解析の結果はグラフで見る形です。オーバーシュートの量や真円度などの数値は出しません |
| 設定値は手入力 | 真円精度では半径と中心座標を、直線精度では基準直線の始点・終点を、利用者が入力します |
| 取得と解析が別々 | ロギングはセッティング PC、解析は TPC-Excel と、2 つのソフトを使い分けます |

### 課題

TPC ロギングは、テクノ製コントローラの強みです。しかし、次の理由で十分に使われていないと考えています。

- **TPC-Excel は Microsoft Excel の仕様に左右されます。** 実際に Excel の版ごとに別のファイルを用意してきました。テクノの判断だけでは、機能の改良や長期の保守ができません。
- **TPC ロギングで取れるデータの一部しか使っていません。** 入出力の状態やステータスも同期して記録できるのに、TPC-Excel が解析するのは位置だけです。
- **ユーザーにとって重要なユースケースを、十分につかめていません。** テクノが有用と考えるユースケースが、ユーザーにとって本当に重要か、どれだけよく起きる困りごとなのかは、確かめられていません。
- データの取得（セッティング PC）と解析（TPC-Excel）が別々のソフトで、CSV の受け渡しが必要です。
- 解析の結果がグラフだけなので、良し悪しの判断が見る人の経験に頼りがちです。

## 3. 目的

1. TPC-Excel の解析機能を引き継ぎ、Excel に頼らないテクノ独自のアプリケーションにします。
2. データの取得から表示・解析までを、1 つのアプリでできるようにします。
3. 位置だけでなく、入出力やステータスなど TPC ロギングで取れるデータを広く活用します。
4. ユーザーの声をもとに、ユースケースを継続して見つけ、確かめ、機能に育てる仕組みを作ります（6 章）。
5. TPC ロギングのデータを有効に使うと、さまざまな恩恵があることを、ユーザーに知ってもらいます。

## 4. 想定する利用者

| 利用者 | 主な使い方 |
|---|---|
| 社内の開発・技術者 | 装置やソフトの開発で、調整や不具合の解析に使います |
| フィールド・サービス担当 | 客先での立上げやトラブル対応で、その場でデータを取って確認します。ユーザーへのデモにも使います |
| 顧客（装置ユーザー） | 製品に付けて提供し、自分の装置の状態を確認・解析するのに使います |

TPC-Excel の説明書は、TPC ロギングの応用として、サーボ調整、サーボ系の調査（メカのガタ、ロストモーション、スティックモーション）、開発支援、不具合の解析、機械の出荷試験を挙げています。これらの場面で、上の利用者が使うことを想定します。

## 5. ユースケース

ユースケースは次の 2 つに分けて扱います。

| 区分 | 内容 | 状態 |
|---|---|---|
| A. TPC-Excel から引き継ぐもの | 5-1〜5-3 の 3 つの解析 | 計算の中身は確認済み。ユーザーにとっての重要度は 6 章の進め方で確かめます |
| B. 新しいユースケースの候補 | 5-5 の候補 | テクノの **仮説** です。6 章の進め方で、重要度と頻度を確かめてから採用を決めます |

### 5-1. サーボ応答精度解析

| 項目 | 内容 |
|---|---|
| 場面 | 立上げや調整で、サーボのゲインなどを決めるとき |
| 記録するデータ | 1 つの軸の指令位置と機械位置。完全に同期して記録しているので、2 つを重ねるとサーボの遅れや揺れが一目で分かります |
| TPC-Excel の計算 | 隣り合う点の位置の差を制御周期で割って、速度（pulse/s）を求めます。1 列目と 2 列目の速度を、時間を横軸にして重ねて描きます。入力するのは制御周期（ms）だけです |
| 分かること | 追従性、オーバーシュート、定常速度、速度リップル |
| アプリで加える機能（案） | オーバーシュート量、整定時間、速度リップルなどを数値で出します。指令と実際の差（追従誤差）も表示します |
| ユーザーの恩恵 | 調整の結果をその場で確かめられ、良し悪しを数値でも判断できます。調整の時間が短くなり、品質がそろいます |

### 5-2. 真円精度解析

| 項目 | 内容 |
|---|---|
| 場面 | 2 軸で円を描かせ（円弧補間）、軌跡の精度を確かめるとき |
| 記録するデータ | 2 軸の機械位置 |
| TPC-Excel の計算 | 利用者が入力した中心座標と半径の理想円に対して、各点の実際の半径との差を求めます。差を「標準偏差スケール」で拡大し、理想円と ±スケールの円と一緒に描きます。開始点と、開始から 30° までの範囲を色を変えて描きます |
| 分かること | 2 軸のゲインバランス、象限が切り替わるときの突起状の誤差、摩擦によるスティックモーション、低速送りの速度ムラによる軌跡誤差 |
| アプリで加える機能（案） | 中心と半径をデータから自動で求めます（最小二乗法など）。真円度（半径の誤差の最大と最小の幅）を数値で出します |
| ユーザーの恩恵 | 設定の手間が減り、軸の間の応答の差や動く向きが変わるところの乱れを、数値の根拠つきで見つけられます |

### 5-3. 直線精度解析

| 項目 | 内容 |
|---|---|
| 場面 | 2 軸を同時に動かして直線を描かせ（直線補間）、軌跡の精度を確かめるとき |
| 記録するデータ | 2 軸の機械位置 |
| TPC-Excel の計算 | 利用者が入力した始点・終点を結ぶ理想直線に対して、各点から直線へ垂直に下ろしたずれを求めます。ずれの大きさと、その X 成分・Y 成分の 3 つを、データ番号を横軸にして描きます。解析に使うデータの範囲（何番目から何番目まで）を指定できます |
| 分かること | 2 軸のゲインバランス、摩擦によるスティックモーション、低速送りの速度ムラによる軌跡誤差 |
| アプリで加える機能（案） | 基準直線をデータから自動で求めます。ずれを、直線のどちら側かが分かる符号つきで表示します。ずれの最大値などを数値で出します |
| ユーザーの恩恵 | 加工や搬送の精度が出ているかを、数値の根拠つきで確認・説明できます |

### 5-4. TPC-Excel からの進化点（案）

2 章で分かった制約を、次のように解消します（要確認）。

| TPC-Excel の制約 | アプリでの進化点 |
|---|---|
| 機械位置だけを取り、手入力した理想の軌跡と比べる | 軸ごとに仮想指令位置（理想の軌跡）、指令位置（フィルターをかけてサーボに払い出す指令）、機械位置を同時に記録します。比べる組み合わせを変えると、ずれが指令とサーボ側のどちらで生じたかを分けて調べられます（RTMC64-EC で確認） |
| Excel の版に依存する | Excel を使わない独自アプリにし、テクノの判断で改良・保守できるようにします |
| 取得と解析が別々 | コントローラからデータを読み出し、そのまま解析・表示します。CSV の受け渡しが要らなくなります |
| 位置の 2 列だけを扱う | 入出力、ステータス、トルクなども表示・解析できるようにします（5-5） |
| 結果は主にグラフ | 5-1〜5-3 の数値の指標を出します |
| 設定値は手入力 | 円の中心・半径や基準直線を、データから自動で求めます |
| 32,000 点まで | 長い時間の記録を扱えるようにします |
| （なし） | ロギング中のデータを、その場でグラフに表示します（第 1 段階には入れません。7 章） |

このうち、第 1 段階に入れるものは 7 章「第 1 段階の範囲」に書きました。

### 5-5. 新しいユースケースの候補（仮説）

TPC ロギングでは、位置と同じ周期で、入出力の状態、ステータス、アラーム、トルクなども記録できます。
これらと位置を **同じ時間軸で突き合わせる** と、TPC-Excel ではできなかった分析ができると考えています。

下の表は、発案者が考えた最初の候補です。**ユーザーにとって重要か、どれだけよく起きるかは、まだ確かめていません。** 6 章の進め方で確かめ、候補を増やしたり絞ったりします。

| 候補 | 使うデータ | 分かること・想定する場面 |
|---|---|---|
| 入出力のタイミングと位置の関係 | 位置、入力信号、出力信号 | センサが反応した位置、出力を出した位置を、軌跡の上や時間軸の上に重ねて表示します。センサの検出位置のばらつきや、出力の遅れを確かめられます |
| 動作の時間の分解（タクトタイム） | 位置、入出力、タスクステータス | 移動、待ち、入出力の待ち合わせなど、1 サイクルの時間が何に使われているかを分けて表示します。サイクルタイムの短縮に使えます |
| アラームが起きる前後の再現 | 位置、偏差量、トルク、アラーム、ステータス | アラームが起きた時点の前後で、何が起きていたかをさかのぼって確かめます。再現しにくい不具合の解析に使えます |
| 負荷の変化の監視 | 偏差量、トルク | 同じ動作での偏差量やトルクを、日ごと・ロットごとに比べます。メカの摩耗や異常の兆しに気づけます（予防保全） |
| プログラムの進み具合との対応 | 位置、マクロ変数、タスクステータス | 運転プログラムのどの段階で、軌跡の乱れや待ちが起きたかを結びつけます |

## 6. ユースケースを見つけて増やす進め方

### 考え方

テクノが「役に立つ」と考えるユースケースと、ユーザーが本当に困っていることは、同じとは限りません。
そこで、ユースケースは **仮説として集め、ユーザーの声で確かめてから採用する** という進め方をとります。この進め方は、最初のリリースの後も続けます。

### 情報を集める方法

| 方法 | 主な担当 | 集めるもの |
|---|---|---|
| 社内のブレーンストーミング会議 | 開発・技術者、フィールド・サービス担当 | TPC ロギングで取れるデータから考えた、活用のアイデア |
| 営業によるユーザーへのヒアリング | 営業 | ユーザーが抱えている技術的な課題、その頻度と重要さ |
| サポートの問い合わせや、トラブル対応の記録（案） | フィールド・サービス担当 | 実際によく起きている不具合と、その調べ方 |
| デモや試用版へのユーザーの反応（案） | 営業、フィールド・サービス担当 | 試作した機能が役に立つか、足りないものは何か |

### ヒアリングで聞くこと（案）

営業がユーザーに聞くときは、次の項目をそろえて聞きます。項目をそろえると、あとで比べたり数えたりできます。

| 項目 | 例 |
|---|---|
| 装置と用途 | 加工機、搬送装置、組立装置など |
| 困っていること | 精度が出ない、原因の分からない停止がある、サイクルタイムを縮めたい など |
| どれくらい起きるか | 毎日、月に数回、立上げのときだけ など |
| 今どう調べているか | 測定器を持ち込む、勘と経験、調べられていない など |
| 解決すると何が良くなるか | 調整の時間、不良の数、停止の時間 など |

### 進め方の流れ

1. **集める**: 上の方法で、アイデアと課題を集めます。
2. **台帳にまとめる**: ユースケースの候補を 1 つの台帳にまとめます。出どころ（社内のアイデアか、ユーザーの声か）も書きます。
3. **評価する**: 下の評価の観点で、候補に点を付けます。
4. **選ぶ**: 点の高い候補から、次に作るものを選びます。
5. **試作して見せる**: 小さく作り、ユーザーに見せて反応を確かめます。
6. **見直す**: 反応をもとに、台帳と評価を更新します。1 に戻ります。

### 評価の観点

| 観点 | 見ること |
|---|---|
| 重要度 | 解決しないと、ユーザーにどれだけの損があるか |
| 頻度 | 何社のユーザーが困っているか、どれくらいよく起きるか |
| 実現性 | TPC ロギングで取れるデータで実現できるか。どの製品で使えるか |
| TPC ロギングらしさ | 「制御と完全に同期した記録」という強みが活きるか。ほかの道具では難しいか |

「TPC ロギングらしさ」を観点に入れるのは、このアプリの目的が TPC ロギングの価値を伝えることだからです。

## 7. 開発の範囲

### 段階的に進める内容

| 段階 | 対象製品 | 内容 |
|---|---|---|
| 第 1 段階（最初のリリース） | RTMC64-EC | 5-1〜5-3 の 3 つの解析を使えるようにします。コントローラからの取得と、5-4 の進化点の多くも含めます（下の「第 1 段階の範囲」）。並行して、6 章の進め方でユースケースを集め始めます |
| 第 2 段階以降 | RTMC64（-M3 / -EC）、PLMC-M3EX、SLM8000 | 6 章で選んだユースケースを順に追加します。製品ごとの通信ライブラリの違いを吸収し、対応製品を広げます |

### 第 1 段階の範囲

[ADR-001](../02_design/decisions/ADR-001_phase1-scope.md) で決めました。要点は次のとおりです。

| 区分 | 内容 |
|---|---|
| 対象 | ユースケースは 5-1〜5-3 の 3 つだけです。対応する機種は RTMC64-EC だけです |
| 取得 | コントローラから直接ロギングし、読み続けてバッファより長く記録します。軸ごとに仮想指令位置、指令位置、機械位置の 3 種類を、2 軸分（6ch）同時に取ります。CSV に保存でき、TPC-Excel 形式（2 列）でも書き出せます |
| 解析と表示 | TPC-Excel 形式の CSV を読み込み、TPC-Excel と同じ計算で解析できます。3 つの位置の比較、数値の指標、中心・基準直線の自動推定などの進化点を加えます。グラフを印刷・画像保存できます |
| 入れないもの | ロギング中のリアルタイム表示（読み出しを遅らせるおそれがあるため。将来の候補として [バックログ](../02_design/backlog.md) で管理します）、RTMC64-M3 への対応、5-5 の新しいユースケース |

開発は、動作を段階ごとに確かめられるよう、3 つの仕様（spec）に分けて進めます。

| spec | 中身 | 実機 |
|---|---|---|
| 001 | 画面の土台、CSV の読み込み、3 つの解析（TPC-Excel と同じ計算）、グラフの表示・印刷・画像保存 | 不要 |
| 002 | コントローラからの取得、CSV 保存 | 必要 |
| 003 | 解析の進化点 | 不要 |

3 製品とも同じ種類のマニュアル（通信ライブラリ、送受信データ）がそろっています（[オンボーディング資料 8 章](../00_onboarding/onboarding_dev.md#8-資料の読み方)）。

### 技術的な前提

- C# の Windows アプリケーションとして、Visual Studio 2019 で開発します。
- コントローラとは、テクノの通信ライブラリ（DLL）を通してやり取りします。
- Microsoft Excel がなくても動くようにします。
- ユースケースを後から増やしていくので、**解析の機能を追加しやすい作り** にします。データの取得、表示、解析を分けて作り、新しい解析を足すときにほかの部分を直さずに済むようにします。
- 製品ごとの違いも、差し替えやすい作りにしておきます。

## 8. リスクと対策

| リスク | 対策（案） |
|---|---|
| 開発機や客先の装置は実機につながっており、アプリの操作で装置が動くおそれがある | 第 1 段階では、アプリがコントローラに送るコマンドを、ロギングの設定・開始・停止とデータの読み出しに限ります。運転の指令は送りません。ユースケースによっては、将来、運転の指令（自動で生成したものを含む）を送る機能を加えることを検討します。その場合は、送る前に毎回、警告と指令の内容を表示して利用者の承認を得ることなどを必須にします（[constitution](../../.specify/memory/constitution.md) 原則 I） |
| Windows はリアルタイム OS ではないので、読み出しが遅れてバッファが一杯になり、ロギングが止まるおそれがある | バッファの使用量を見ながら読み出す間隔を調整し、止まったときは画面で知らせます。TPC-Excel の説明書も、ロギング周期を長くする（一般的な軌跡精度の解析なら 4 ms 程度で十分）ことを勧めています |
| 解析の結果が TPC-Excel と食い違い、ユーザーが戸惑う | TPC-Excel と同じ計算式で作ります。TPC-Excel に付いているサンプルデータ（サーボ応答用 3 つ、真円用 2 つ）を両方で解析し、結果が一致することを確かめます |
| TPC-Excel を使っているユーザーが移行しにくい | TPC-Excel と同じ形式の CSV（1 行 1 点、2 列）を読み込めるようにし、これまでに取ったデータも解析できるようにします。アプリで取ったデータも、同じ形式で書き出せるようにします |
| TPC-Excel が新しい Excel（Office 2024）で正常に動かず、アプリができるまでユーザーが解析できない | 当面は TPC-Excel を保守し、アプリと並行して提供します。Office 2024 で動くように、別のリポジトリで直します。解析の計算は変えません（[ADR-002](../02_design/decisions/ADR-002_tpcexcel-maintenance.md)） |
| テクノの思い込みで機能を作り、ユーザーに使われない | 6 章の進め方で、ユーザーの声を確かめてから作ります。小さく試作して反応を見ます |
| ヒアリングが続かず、ユースケースが増えない | 聞く項目と台帳の形を決めておき、営業の通常の訪問で聞けるようにします。担当と頻度を決めます（9 章） |
| 製品ごとに通信ライブラリやデータの形式が違う | 通信部分を製品ごとに分けて作ります |
