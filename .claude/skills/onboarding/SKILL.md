# オンボーディング資料の作成・更新

TPCVisualLoggingApp に新しく参加する開発者が、初日に読んで作業を始められる資料を作る。
資料の中身はこのファイルに書かず、**毎回リポジトリの現状を調べて書く**。推測で書かないこと。

## 出力先

- `docs/00_onboarding/onboarding.md`（既にあれば読んでから更新する。人が手で書き足した部分は消さずに残す）
- 画像や補足が増えたら同じフォルダに置く

## docs/ の構成と、この資料の役割

| フォルダ | 中身 |
|---|---|
| `00_onboarding/` | この資料。最初に読む入口 |
| `01_project/` | プロジェクトの背景・会議資料 |
| `02_spec/` | 要件・仕様 |
| `03_reference/<製品>/` | 製品ごとのマニュアル（`rtmc64/`、`plmcm3ex/`、`slm8000/` など）。原本の PDF は `source/`、Markdown 版は `converted/` |
| `04_dev/`（今後作る予定） | コーディング規約・詳しいビルド手順などの開発ガイド |

- この資料は「初日に読むもの」と「01〜04 をどの順で読むか」の案内に絞る
- 01〜04 の本文は写さず、要約（数行）とリンクにする。同じ内容を 2 か所に書くと食い違いが生じるため
- `04_dev/` があれば、規約や詳しい手順はそちらへリンクし、この資料には最低限だけ書く

## 手順

### 1. 現状を調べる

次を読み、資料に書く事実を集める。存在しないものは飛ばす。

- `AGENTS.md` / `CLAUDE.md` — AI エージェント向けのルール
- `.claude/README.md` と `.claude/settings.json` — 権限設定と、その前提（実機接続など）
- `scripts/` 配下 — ビルドや変換スクリプトの使い方（ファイル冒頭のコメント・引数）
- ソリューション (`*.sln`)・プロジェクト (`*.csproj`) — ターゲットフレームワーク、プロジェクト構成、参照 DLL
- `docs/01_project/` — 背景・目的・関係者（会議資料は一覧と日付だけ把握すればよい）
- `docs/02_spec/` — 要件・仕様の一覧と、それぞれ何を決めた文書か
- `docs/03_reference/<製品>/` — 製品フォルダの一覧と、製品ごとのマニュアルの一覧・内容。`converted/` がない PDF は 1 ページ目を読んで題名と内容をつかむ。フォルダしかない製品は「未整備」とする。あわせて、全ページに「社内文書」「提出不可」「社外秘」などの記載がないか調べ、見つかったらファイル名とページを報告してユーザーに扱いを確認する（マニュアルは公開物だけを置く方針のため）
- `docs/04_dev/` — あれば、開発ガイドの一覧
- `.gitignore` / `.gitattributes` — 開発環境の前提
- `git log --oneline -30` と `git branch -a` — ブランチ運用（`develop` / `master`）と最近の変更

### 2. 資料を書く

構成は次を基本とする。調べて書く内容がない章は「未整備」と明記して残す（空欄を埋めるために推測しない）。

1. **このプロジェクトについて** — 何を作っているか、対象の装置・コントローラ。`01_project/` の要約とリンク
2. **最初に知っておくべき注意** — 開発機が実機のコントローラ (RTMC64) に DLL 経由でつながっていること。exe やテストを実行すると実機に指令が届くおそれがあること。必ず冒頭近くに置く
3. **開発環境のセットアップ** — 必要なツール（Visual Studio 2019 など）とバージョン、Python 仮想環境 (`.venv`) の作り方、クローン後にやること
4. **リポジトリの構成** — 主要フォルダ・ファイルとその役割を表で
5. **ビルドと実行** — `scripts/build.ps1` の使い方、実行時の注意
6. **ブランチとコミットの運用** — ブランチの使い分け、コミットメッセージの書き方（git log から読み取れる慣習）
7. **Claude Code を使うとき** — 権限設定の要点（詳細は `.claude/README.md` へリンク）、`AGENTS.md` のルール
8. **資料の読み方** — `01_project/` → `02_spec/` → `03_reference/`（→ `04_dev/`）の順に、主な文書へのリンクと一行説明。`03_reference/` は製品ごとに表を分ける。最初に読むべきものに印を付ける
9. **困ったときは** — 問い合わせ先など（リポジトリから分からなければ「未整備」とし、ユーザーに確認を促す）

### 3. 書き方

- 読み手は「C# は書けるが、このプロジェクトと装置は初めて」の開発者。社内用語や略語は初出で説明する
- 日本語で、です・ます調。手順は番号付きリスト、コマンドはコードブロックにする
- ファイルへの言及は相対パスの Markdown リンクにする（例: `[build.ps1](../../scripts/build.ps1)`、`[仕様](../02_spec/)`）
- 冒頭に「最終更新日」と「この資料は `/onboarding` skill で生成・更新している」旨を書く

### 4. 終わったら

- 前回からの主な変更点と、「未整備」として残った章をユーザーに報告する
- コミットはユーザーに頼まれたときだけ行う
