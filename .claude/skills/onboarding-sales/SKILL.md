# 営業担当向けオンボーディング資料の作成・更新

TPCVisualLoggingApp を初めて担当する営業担当者が、**お客様に何を伝えてよいか・何を聞いてくればよいか** を理解できる資料を作る。
資料の中身はこのファイルに書かず、**毎回リポジトリの現状を調べて書く**。推測で書かないこと。

## 出力先

- `docs/00_onboarding/onboarding_sales.md`（既にあれば読んでから更新する。人が手で書き足した部分は消さずに残す）
- 開発者向けの `docs/00_onboarding/onboarding_dev.md` とは別ファイル。開発環境・ビルド・Git・Claude Code の話は営業向けには書かない

## 読み手

- テクノ製のモーションコントローラ（RTMC64 など）を売った経験はあるが、ソフトウェア開発や TPC ロギングの中身には詳しくない営業担当者
- Git やリポジトリは使わない前提。資料単体で読めるようにする（リンクは「詳しく知りたい人向け」の補足扱い）

## 手順

### 1. 現状を調べる

次を読み、資料に書く事実を集める。存在しないものは飛ばす。

- `docs/01_project/proposal.md`（企画書）— 概要、背景（TPC ロギング・TPC-Excel・課題）、目的、想定する利用者、ユースケース、進め方、開発の範囲、リスク、決まっていないこと。**この資料の主な情報源**
- `docs/01_project/` のほかの文書 — 会議資料などで決定事項が更新されていないか
- `docs/02_spec/` — あれば、決まった要件・仕様（企画書の「案」が確定したかどうかの確認に使う）
- `docs/03_reference/` — 対象製品（フォルダ名）と、TPC-Excel の説明書（`tpcexcel/`）。製品の正式名称や対応機種は PDF / Markdown から確認する
- `git log --oneline -30` — 最近どこまで進んだか（企画段階か、開発中か、リリース済みか）

### 2. 情報の確度を分ける

営業資料で一番まずいのは、**決まっていないことをお客様に約束してしまうこと**。集めた事実を次の 3 つに分けて書く。

| 区分 | 例 | 資料での扱い |
|---|---|---|
| 確定・提供済み | TPC-Excel の既存機能、コントローラの TPC ロギング機能 | そのまま説明してよい |
| 計画中（企画書で決めた方針） | TPC-Excel の 3 解析の引き継ぎ | 「予定」「計画中」と明記。時期は書かれていれば書く |
| 案・仮説・未定 | 新しいユースケースの候補、進化点の案、体制・スケジュール・価格 | 「検討中。お客様への約束は不可」と明記し、ヒアリング材料として扱う |

- 企画書の「状態」がドラフトなら、資料の冒頭にもその旨を書く
- 価格・リリース時期・対応機種が文書にないときは「未定」と書き、推測で埋めない

### 3. 資料を書く

構成は次を基本とする。書く内容がない章は「未整備」と明記して残す。

1. **このページの使い方** — 誰向けか、最終更新日、情報の確度の区分（上の表）の読み方
2. **ひとことで言うと** — TPCVisualLoggingApp とは何か（2〜3 文）。お客様にそのまま言える言い回しで
3. **お客様にとってのメリット** — 解決する課題と、それによって何が良くなるか。技術用語ではなく現場の言葉で（例: 「加工精度の悪化の原因を、測定器なしで切り分けられる」）。企画書の目的・課題から引く
4. **基礎知識** — TPC ロギングとは何か、TPC-Excel とは何か、新アプリとの関係。用語は初出で平易に説明し、末尾に **用語集** を置く
5. **どんなお客様に向くか** — 想定する利用者・業種・場面。対象のコントローラ
6. **できること（予定を含む）** — ユースケースごとに「何が分かるか」を 1〜2 文で。確度の区分を必ず付ける
7. **お客様に話すときの注意** — 約束してはいけないこと（未定事項の一覧）、よくある質問と答え方（分からないものは「開発担当に確認」と書く）
8. **お客様から聞いてきてほしいこと** — 企画書の「ヒアリングで聞くこと」を、営業が商談で使える質問の形にする。聞いた内容の渡し先も書く（リポジトリから分からなければ「未整備」）
9. **今の状況と今後** — 企画・開発のどの段階か、決まっていないこと
10. **詳しく知りたいとき・問い合わせ先** — 企画書やマニュアルへのリンク、担当者（文書に書かれた発案者など。分からなければ「未整備」）

### 4. 書き方

- 日本語で、です・ます調。1 文を短く、専門用語は最小限にする。コードやコマンドは書かない
- 社内文書の本文は写さず、営業の言葉に要約する。数値や仕様（チャンネル数など）は出典の文書名を添える
- ファイルへの言及は相対パスの Markdown リンクにする（例: `[企画書](../01_project/proposal.md)`）
- 冒頭に「最終更新日」「この資料は `/onboarding-sales` skill で生成・更新している」「社内向け資料であり、そのままお客様に渡さない」旨を書く
- 「社内文書」「社外秘」と書かれた資料から得た情報は、お客様に話してよい内容か分からないため、使った場合はユーザーに報告して扱いを確認する

### 5. 終わったら

- 前回からの主な変更点、「未整備」「未定」として残った項目、企画書と他の文書で食い違っていた点をユーザーに報告する
- コミットはユーザーに頼まれたときだけ行う
